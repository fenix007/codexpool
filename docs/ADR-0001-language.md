# ADR-0001: Как ускорять Codex-путь — развивать stable-форк или выносить пул Codex в отдельный сервис

Статус: **на рассмотрении** (редакция 2, 23.09.2026). Решение принимается пользователем по данным бенчмарка (фаза 0 ниже).

Первая редакция (22.09) называлась «Язык реализации — Rust» и исходила из двух ошибочных посылок: (1) что продакшен работает на «голом» OmniRoute без собственных правок; (2) что главная потеря TTFT — новое WS-соединение на каждый запрос. На деле продакшен — stable-форк с 56 собственными коммитами и зрелым процессом, а транспорт по умолчанию — HTTP; реальная проблема — отключённый keep-alive, и она чинится патчем (`report-stable-hotpath.md`).

## Контекст

- **Продакшен**: fenix007/omniroute `stable` (v3.8.48 + 104 коммита, `3.8.48-fork.N`, `ghcr.io/fenix007/omniroute`), интеграция с ai-router (синхронизация call-log в квоту и `/limits`). Кроме Codex обслуживает другие провайдеры: Kiro, Trae, Gemini, OpenCode Go, xAI, аудио/TTS, картинки.
- **Уже есть в stable для Codex**: стратегия `quota-deadline`, same-account transport retry, немедленный failover инвалидированных OAuth, ретрай другого аккаунта до фолбэка combo, ожидание cooldown, корректные статусы ошибок в SSE, тонкий WS-путь, профилирование рантайма.
- **Потери TTFT в stable** (оценки из кода, до замеров): P1 HTTP без keep-alive (+10–60 мс напрямую, +100–400 мс через прокси); выключенная по умолчанию affinity (потеря prompt-cache — сотни мс – секунды); синхронный preflight (+200–800 мс в p99); хвосты повторов при деградации (до 2× таймаута таргета); 3–6 синхронных записей SQLite, парсинг и копирование тела, Next (в сумме ~5–30 мс CPU).
- **Неустранимо ни в одном варианте**: переключение аккаунта после начала стрима (P6) — свойство протокола Responses.
- **Инвариант**: refresh-токены одноразовые, у каждой учётки — один процесс-владелец.

## Варианты

### A. Развивать stable-форк: патчи горячего пути

Конфиг: `codexSessionAffinityTtlMs` > 0, preflight в фон, лимиты повторов. Патчи: P1 (h2 keep-alive к chatgpt.com без регрессии #4580), P10 (настоящий TTFT в `usage_history`), P3 (записи квоты/breaker/lastUsedAt без await и батчами), P2 (выход из peek после первого не-lifecycle события). Оценка — 300–600 LOC в существующем процессе форка (quality gates, тесты, fork.N).

- **За**: самая дешёвая дорога к крупным выигрышам TTFT; не трогает интеграцию с ai-router и остальные провайдеры; изменения ложатся в уже работающий процесс; нет второго сервиса и второго владельца токенов.
- **Против**: остаётся ~20 модулей на запрос, три системы отказа и пять видов повторов (P8) — система сложна для предсказания; остаётся CPU-overhead Node/Next (P4/P5); каждый патч дальше расходится с upstream (форк уже 4556 коммитов позади, собственные патчи в upstream не уходили); отдельного Stats API нет (есть `/api/usage/*`, `/api/telemetry/summary`).

### B. Выделенный Codex-путь внутри форка

Развить существующий тонкий WS-путь (`scripts/dev/responses-ws-proxy.mjs`) и/или добавить аналогичный HTTP fast-path в `server-ws.mjs`: запросы Codex идут мимо Next и chatCore, выбор аккаунта — через `quota-deadline`, failover — простой цикл до первого байта. Оценка — 300–800 LOC сверх варианта A.

- **За**: снимает P4/P5/P8 для Codex, оставаясь в одном процессе и с одним владельцем токенов; переиспользует stable-код выбора аккаунта, refresh и хранилище.
- **Против**: второй горячий путь в том же кодовом монолите — дублирование логики отказов и учёта; сложнее тестировать; всё ещё Node.

### C. codexpool — отдельный сервис (Rust) только для Codex

Как описано в `architecture.md`: один бинарь, passthrough `/v1/responses`, h2-пул к chatgpt.com, роутер со стратегией `quota_deadline` (портированной из stable), failover до первого байта, отдельный Stats API. Stable остаётся для остальных провайдеров и может ходить к Codex через codexpool как через upstream. Оценка (скорректирована после внешнего ревью): прототип `/v1/responses` с пулом — 2 недели; MVP-1 с импортом, стратегией `quota_deadline`, метриками, тестами и бенчмарком — 3–4 недели одного инженера; MVP-2 (трансляции для Claude Code, Admin API) — ещё 1–2 недели.

- **За**: минимальный и предсказуемый горячий путь (overhead < 5 мс p50 — цель); одна понятная система отказов; настоящий TTFT и Stats API с первого дня; независимость Codex-трафика от релизов форка; Rust-референсы (codex-rs, codex-switcher) снижают риск auth/refresh.
- **Против**: второй сервис в проде; **перенос владения токенами** (учётки нельзя одновременно держать в stable и codexpool); повторная реализация механик, которые stable уже отладил (quota-deadline, retry-политики, корректные статусы ошибок, terminal failures); нужно сохранить учёт для ai-router (call-log) — либо codexpool отдаёт совместимые события, либо stable остаётся в цепочке и логирует.

### Отвергнуто: полная замена OmniRoute

Stable обслуживает много провайдеров вне Codex и интегрирован с ai-router; переписывать всё ради Codex-пути неоправданно.

## Решение: поэтапно, с порогами по данным

**Фаза 0 — замер (обязательно, до любого кода).** Бенчмарк `docs/benchmark.md`: `direct` против `omniroute-stable` (HTTP и WS-путь), серии A–D, параллельно `OMNIROUTE_RUNTIME_DIAGNOSTICS=1` и `OMNIROUTE_TRACE=true`, подсчёт новых TCP-соединений к chatgpt.com при 1/5/20 req/s. Выход: фактический overhead stable над direct (p50/p95), лаг event loop под целевой конкуренцией, error-rate при исчерпанной учётке.

**Фаза 1 — вариант A.** Конфиг + патчи P1, P10, P3, P2 в stable (новый fork.N), повторный бенчмарк.

**Порог перехода к B или C** — после фазы 1, по данным одного прогона, где `direct` и stable меряются в тех же условиях (тот же хост, те же кейсы, перемешанный порядок, одинаковые планы учёток). Срабатывает, если выполняется хотя бы одно:
- overhead stable над `direct` > 50 мс p50 или > 150 мс p95 на серии A — по `ttft_ms` и отдельно по `ttft_text_ms`. Обоснование: 50 мс — это порядок одного RTT до chatgpt.com и примерно 5–10 % TTFT коротких ответов без reasoning (0,5–1 с); на таком масштабе шлюз уже заметен в интерактивной работе. 150 мс p95 ловит хвосты, которые пользователь ощущает как «подвисания». Для reasoning-ответов с TTFT 5–30 с эти пороги строгие — это сознательно: overhead шлюза не зависит от длины reasoning;
- при concurrency 16 рост TTFT p95 у stable больше, чем у `direct` при той же конкурентности, на 20 п.п. и более (сравнение с `direct`, а не с собственной concurrency 1, чтобы отделить деградацию шлюза от деградации upstream), либо лаг event loop p99 > 50 мс при целевой конкурентности;
- error-rate stable выше `direct` на тех же кейсах и в том же окне времени, и разница статистически значима (точный тест Фишера, p < 0,05, не меньше 200 запросов на бэкенд), — в серии C (одна учётка из трёх исчерпана) или C2 (весь пул у лимита);
- поддержка Codex-логики в форке требует больше времени, чем её выделение.

**Выбор между B и C** при срабатывании порога: B, если узкое место — Next/chatCore (видно в CPU-профиле), а Node в целом справляется; C, если упираемся в event loop/GC под нагрузкой, либо нужна независимость Codex-трафика от релизного цикла форка, либо Stats API и предсказуемая система отказов важнее стоимости второго сервиса.

**Язык для C** — Rust (аргументы первой редакции остаются в силе: byte-passthrough без GC, codex-rs и codex-switcher как референсы, нативный `wreq`); Go на SDK CLIProxyAPI — запасной вариант. Для B язык не выбирается — это Node внутри форка.

## Последствия

- Скелет `codexpool/` сохраняется как готовая основа варианта C; в нём стратегия по умолчанию заменяется на портированную `quota_deadline`, а импортёр читает `DATA_DIR/storage.sqlite`.
- Бенчмарк-harness (`bench/`) нужен в любом варианте — это инструмент фазы 0 и критерий всех дальнейших решений.
- Патчи варианта A стоит предлагать upstream отдельными PR — это сокращает патч-сет, который форку приходится нести. Риск: патч P1 меняет диспетчер, который upstream сознательно настроил так из-за #4580, и PR могут отклонить. План от этого не зависит — патчи живут в форке в любом случае.
- Первый шаг фазы 0 — проверка протокола к chatgpt.com с прод-хоста (h2 или HTTP/1.1): от неё зависит вариант патча P1. Из sandbox проектирования это не измерить — egress там перехватывается TLS-прокси.
