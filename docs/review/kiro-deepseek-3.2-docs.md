## 2. Главные 5 рисков

1.  **Протокол upstream неизвестен.** Патч P1 (h2 keep-alive) основан на предположении, что chatgpt.com поддерживает HTTP/2. Если только h1.1, то выигрыш от патча будет ограничен, а риск регрессии #4580 (очередь стримов) остаётся. **Действие:** проверить ALPN в фазе 0.
2.  **Необоснованные пороги перехода.** Критерии в ADR (50 мс p50, 20 % рост p95) не привязаны к базовой линии (`direct`) и могут привести к преждевременному переходу к дорогостоящему варианту C. **Действие:** пересмотреть пороги, используя `direct` как baseline.
3.  **Конфликт refresh-токенов при горизонтальном масштабировании.** В документах рассматривается конфликт между stable и codexpool, но упускается конфликт между несколькими репликами stable, если они появятся в будущем. **Действие:** явно описать ограничение: stable не поддерживает горизонтальное масштабирование для Codex без внешнего координатора refresh.
4.  **Оптимистичные сроки для Rust (вариант C).** Оценка в 2 недели на MVP-1 нереалистична для production-ready сервиса со стратегией `quota-deadline`, импортом, failover и метриками. **Действие:** скорректировать оценку до 3–4 недель, иначе план станет невыполнимым.
5.  **Некорректное измерение TTFT.** Опора на клиентское время «отправки последнего байта» добавит шум в измерения, критичные для целевых 5 мс overhead. **Действие:** модифицировать harness для использования временных меток внутри прокси.

## 3. Что в аудите сделано правильно

1.  **Глубокий анализ кода stable.** Выявлены конкретные коммиты форка (`quota-deadline`, same-account retry), проверены реальные проблемы (P1–P10) по коду, а не по предположениям.
2.  **Обнаружен ключевой инвариант** — одноразовые refresh-токены и конфликт владения. Это блокирующее ограничение для любого выноса.
3.  **Акцент на данные, а не мнения.** Предложена фаза 0 (бенчмарк) до любых решений, что исключает оптимизацию не тех проблем.
4.  **Выявление бесполезной метрики TTFT в stable** (P10). Это предотвратит ложные выводы из внутренней статистики.
5.  **Предложен прагматичный путь** — начать с патчей в форке (вариант A), так как основные потери TTFT (keep-alive, affinity, preflight) не связаны с языком.

## 4. Вердикт по ADR

ADR предлагает обоснованный поэтапный подход, но содержит технические неточности (keep-alive, h2) и слабые критерии перехода. **Основная логика верна:** сначала замерить, затем патчить stable, и только при явных ограничениях Node.js рассматривать вынос. Решение должно опираться на **бенчмарк, где baseline — `direct` вызов**, а пороги перехода — на статистически значимое отставание stable от этого baseline после патчей. Перед фазой 0 необходимо уточнить методику измерения TTFT и проверить поддержку h2 upstream.
